# Static review: short 8 MiB scheduled DDS/DMA queue failure

**Finding:** the strongest source-based diagnosis is exhaustion of the historical host DMA **outgoing queue**, shared across traffic classes, probably its 32 MiB byte cap. The exact throw site, byte-versus-message trigger, occupancy, and packet/retransmission history are not recorded. This is an inference, not a stack-confirmed diagnosis. No execution, tests, builds, runtime probes, simulation, rerun, relabel, or asset/tooling changes were performed for this review.

**Observed evidence.** In `.chimaera-m5/timing-short-r3/`, the twelve `*/benchmark-attempt.json` records show eleven complete cases and one failure, including completion of all eight baseline Chimaera cases. The exception is `short-bulk8m-scheduled_dds_dma-chimaera-shm-r1` (abbreviated **F** below): `driver.log:6` says `Latency driver: controller queue limit exceeded`; `run.json:50,75` and `benchmark-attempt.json:64,170` retain failure. The Python traceback at attempt line 171 reports the launcher detecting that error; it supplies no C++ stack. The four preceding IP-selection warnings do not establish the queue failure's cause.

## Exact limits and runtime configurability

- **Generic defaults:** `OutgoingQueue` defaults to **1,024 messages / 33,554,432 bytes (32 MiB)**; its C++ constructor accepts count and byte limits (`A:T/include/chimaera/outgoing_queue.hpp:11–24`). Either limit produces the recorded text at lines 43–44.
- **Historical DMA outgoing, actual Fast DDS path:** **8,192 messages / 32 MiB**, one queue per controller, shared across traffic classes. `Bridge::controller_queue_limit()` returns the literal 8192 when its DDS router exists (`A:R/include/chimaera_ros_bridge/bridge.hpp:301–305`). The timing wrapper passes that count to `DmaHostController` (same directory, `gazebo_timing_controller.hpp:34–36`); its implementation constructs `outgoing(pending)` without supplying a byte limit (`A:T/src/dma_host_controller.cpp:8–21`). The public DMA constructor defaults to 1024 and explicitly documents that the 32 MiB cap remains (`A:T/include/chimaera/dma_controller.hpp:12–15`). This is not one 32 MiB pool combining both directions.
- **Historical DMA incoming:** **1,024 messages / 32 MiB**, independently of the outgoing count override (`A:T/src/controller_protocol.hpp:20–43`; `dma_host_controller.cpp:12,60–68`). `ReceivedQueue::append` has the other identical exception at line 43. Guest DMA likewise uses `outgoing(pending)` and the fixed `ReceivedQueue` (`A:T/src/dma_guest_controller.cpp:99–117,244,287–293`); its bridge supplies the same DDS count (`A:R/src/guest_bridge.cpp:64–69`).

**There is no existing runtime parameter to enlarge these historical controller byte caps.** `max_pending_messages` and `max_serialized_bytes` configure the bridge's application queue/message bounds; the Fast DDS controller count is independently hardcoded to 8192. The latency driver forwards selected bridge parameters, not a controller byte-budget setting (`A:R/benchmark/driver.cpp:130–152`; bridge header lines 38–52,285–305). Changing these compiled controller limits requires a changed build and therefore a separately identified comparison variant.

`F/driver.yaml:19` sets `max_serialized_bytes=8392704` (8 MiB + 4096); `guest-session.json:41` sets 16781312 (16 MiB + 4096). Neither sets aggregate controller storage. DDS QoS depth 128, DDS shared memory 67108864, DDS max-message size 9433088, and kernel `buffer_mb=9 receive_slots=16 transmit_slots=4` are separate bounds (`F/run.json:21,43–48`; `guest-session.json:45`; bulk routes at `routes.json:109–133`). Increasing those values does not enlarge the 32 MiB queue. The historical DDS router itself defaults to 64 MiB and reports a different error, `DDS runtime queue capacity exceeded` (`A:ros/chimaera_ros_ws/src/chimaera_dds_transport/include/chimaera_dds_transport/router.hpp:19`, `src/router.cpp:81–84`).

## Why outgoing is the stronger candidate

The DDS exchange drains router packets into `controller.submit()` until empty, before the controller's next step can move its outgoing queue into mailboxes (`A:R/include/chimaera_ros_bridge/bridge.hpp:276–291`; `A:T/src/dma_host_controller.cpp:23–29,44–51`). A burst can therefore exceed the outgoing queue even though downstream mailbox capacity exists.

Conversely, each normal exchange first drains controller incoming messages. The host performs an exchange before stepping and appends received output only once per step (`A:R/include/chimaera_ros_bridge/gazebo_timing_controller.hpp:88–100`; `A:T/src/dma_host_controller.cpp:60–68`). On an empty incoming queue, an oversized new batch is rejected earlier by `bytes(source)` with **different** text, `controller queue exceeds 32 MiB` or `controller queue exceeds 1024 messages` (`A:T/src/controller_protocol.hpp:20–43`). That makes the generic incoming-accumulation exception a weaker explanation for this host log. The log alone still cannot prove which limit fired.

The recorded workload is the authorized **0.2 s source / 0.05 s warmup / 0.1 s drain**, 8 MiB at 5 Hz, burst 1, both directions, with cameras and control background (`F/benchmark-attempt.json:19–54`; `host.yaml:8–18,28–32`). The common endpoint schedules releases at 0 and 0.2 s before its 0.25 s stop: one warmup sample plus one source-window sample per direction, not sustained bulk traffic. See `profiling/chimaera_m5/endpoint.cpp:105–115,233–239,370–381,416–438`; its SHA-256 matches the lock's benchmark source (`99d00982c82615cf78e58260c3c57c25ee2ade134dedd7af943bb41a5b74489e`). These are intended releases, not proof the failed run completed them.

Adding both directions' application bytes does **not** prove exhaustion of one queue. RTPS framing, fragmentation, discovery/reliability traffic, possible retransmissions, and paused-boundary accumulation can change queued bytes. The historical custom DDS descriptor advertises 1 MiB packets (`A:ros/chimaera_ros_ws/src/chimaera_dds_transport/include/chimaera_dds_transport/transport.hpp:13`; `src/transport.cpp:325–326`), so an application Image is not a single queue entry. No measured amplification or precise overflow sequence is available.

## Comparison and parent disposition

The new `M5HostController` has **two independent lanes**, each with **8,192 outgoing messages / 128 MiB** and **8,192 incoming messages / 640 MiB** in this DDS construction path (`B:T/src/m5_host_controller.cpp:15–16,35–54`; `B:R/include/chimaera_ros_bridge/bridge.hpp:324–328`). These are logical caps, allocated for actual messages, not measured resident memory. Its backpressure path retains accepted frames when capacity is unavailable; control and bulk have independent credits (`B:T/src/m5_host_controller.cpp:71–80,108–148`). Historical DMA shares each directional queue across classes. Queue capacity, isolation, admission/backpressure, and packetization therefore differ alongside the transport mechanism.

The completed new bulk case and failed historical DMA bulk case support a **completion/resource-limit comparison under their frozen configurations**. They do not provide a numeric DMA-to-m5ops latency or throughput speedup; failure time is not a completed-work runtime. One source-window bulk sample per direction also cannot establish sustained throughput or meaningful bulk tail percentiles. Larger buffers and separate lanes can improve burst acceptance while changing memory use and delay; this run cannot isolate those effects from transport cost or establish fairness under sustained contention.

**Disposition:** preserve the twelve original outcomes and describe the unequal budgets explicitly. No demonstrated launch-configuration error causing this exception was found: the shortened timing, payload headroom, backend, and module options agree with the recorded request. Correct any configuration/reporting assumption that DDS SHM size, DMA slots, or bridge `max_serialized_bytes` sets the controller byte budget; none does. An equal-budget or isolated-mechanism comparison would need a separately specified variant. Do not automatically rerun, rebuild, relabel, or add stepped-native work.
