# Static review: short 8 MiB direct DDS + m5ops stalls

The throughput-with-small-control-latency goal remains unmet. The new path completes the finite 8 MiB transfers, but joints and clock callbacks stall for more than 120 ms, and effort generation misses scheduled releases. The strongest explanation supported by the endpoint source and event ordering is shared application execution around bulk publication and typed reception. A participant-wide DDS send critical section is also proven in source. The retained events do **not** measure time inside serialization, deserialization, allocation, transport submission, or locks, so they cannot assign the observed milliseconds to those stages.

This review used existing JSON/CSV arithmetic, hashes, configuration, and source reads only. No builds, tests, probes, simulations, native runs, or subdelegation were performed. Only this file was written. The supplied successful KVM catch/qualification context is separate from the timing measurements below; the timing report records two active `BaseTimingSimpleCPU` cores at 3 GHz, not active KVM CPUs.

All latency values below are simulation-time milliseconds from the source's pre-`publish()` marker to callback entry. They include application/executor and typed-take costs as well as transport. They are not transport-only measurements.

- Joints: unloaded p50/max **0.177754 / 7.044554**, loaded **41.433014 / 123.383795**; 50/50 measured publications received in both. Loaded scheduled-to-callback age exceeds the report's 10 ms deadline for **34/50** receipts.

- Left image: unloaded p50/max **3.552860 / 5.016561**, loaded **31.188625 / 91.169836**. Right image: **5.388330 / 6.976024** becomes **32.955326 / 93.316567**. Each has six measured publications and receipts; each loaded eye has three scheduled-age deadline misses.

The report selects its source cohort by **actual publication time**, while scheduled-release coverage is selected independently by **scheduled time** ([metrics.py](/home/kkgiorgos/Chimaera/profiling/chimaera_m5/metrics.py:139)). That distinction explains the apparent effort count contradiction: 12 delayed warmup releases (sequences 1–12, scheduled 4–48 ms) enter the publication-time measurement cohort, while 12 late-window releases never occur. The loaded 50/50 receipt count alone does not demonstrate a maintained 250 Hz control source.

Drain matters. Of the measured loaded source cohort, 13 joints, 50 clocks, two images per eye, and both bulk samples arrive at or after 250 ms. No measured transmitted sample is missing at drain, but receipt by cutoff does not imply a small control delay. Source-normalized bulk body delivery is `8 MiB / 0.2 s = 41.94304 MB/source-second` per direction. This is finite-cohort accounting, not a measured maximum transfer rate. The report's one bulk callback per direction **inside** `[50, 250)` ms comes from the warmup sample (sequence 0); the measured sample (sequence 1) arrives in drain. It must not be described as continuous measured-window bulk service. The report itself records insufficient repeated evidence for sustainability/tail claims.

**Source-established shared stages**

- **One application execution thread for sources and all subscriptions.** [endpoint.cpp](/home/kkgiorgos/Chimaera/profiling/chimaera_m5/endpoint.cpp:548) creates one node, one 1 ms source wall timer, and one `SingleThreadedExecutor`. Every typed subscription is created without custom subscription options/callback groups (line 287); the timer also uses its default group (558). Sources and incoming image/control processing therefore have no application executor concurrency. They share the node's default callback group; merely switching to a multithreaded executor while retaining a mutually exclusive default group would not isolate them.
- **Merged source scheduling makes publication a blocking stage for other sources.** [tick_ball](/home/kkgiorgos/Chimaera/profiling/chimaera_m5/endpoint.cpp:416) selects due streams in one loop, calls `stream.publish()` inline, records the event after it returns, then samples time again. [The publish lambda](/home/kkgiorgos/Chimaera/profiling/chimaera_m5/endpoint.cpp:265) samples `now()` immediately before `publisher->publish(*message)`. It cannot advance the next control source or run a subscription concurrently while this call occupies the timer. The loop stops emitting at `stop_`; it does not continue pending source releases during drain. Ordinary RGB images also share this path, so isolating only supplemental bulk would leave camera interference possible.
- **Typed reception includes synchronous deserialization before the callback marker.** [RMW `_take`](/home/kkgiorgos/Chimaera/.chimaera-middleware/rmw_fastrtps-6.2.10/rmw_fastrtps_shared_cpp/src/rmw_take.cpp:89) passes the caller's ROS message to `DataReader::take`. [DataReaderImpl::read_or_take](/home/kkgiorgos/Chimaera/.chimaera-middleware/Fast-DDS-2.6.12/src/cpp/fastdds/subscriber/DataReaderImpl.cpp:440) holds the reader mutex and executes `ReadTakeCommand`; [its typed-sample path](/home/kkgiorgos/Chimaera/.chimaera-middleware/Fast-DDS-2.6.12/src/cpp/fastdds/subscriber/DataReaderImpl/ReadTakeCommand.hpp:348) calls `type_->deserialize` synchronously. [RMW type support](/home/kkgiorgos/Chimaera/.chimaera-middleware/rmw_fastrtps-6.2.10/rmw_fastrtps_shared_cpp/src/TypeSupport_impl.cpp:98) then calls `deserializeROSmessage`, which invokes the generated CDR callback ([type_support_common.cpp](/home/kkgiorgos/Chimaera/.chimaera-middleware/rmw_fastrtps-6.2.10/rmw_fastrtps_cpp/src/type_support_common.cpp:97)). In the normal rclcpp typed-subscription execution path this take runs on the executor before user callback dispatch. The benchmark records `callback_ns` only at user callback entry (endpoint line 288), after that work. A short callback body therefore does not establish cheap receive processing or executor isolation.
- **Publication performs serialization before returning.** [RMW publish](/home/kkgiorgos/Chimaera/.chimaera-middleware/rmw_fastrtps-6.2.10/rmw_fastrtps_shared_cpp/src/rmw_publish.cpp:53) calls `DataWriter::write`; [DataWriterImpl](/home/kkgiorgos/Chimaera/.chimaera-middleware/Fast-DDS-2.6.12/src/cpp/fastdds/publisher/DataWriterImpl.cpp:787) obtains a payload and invokes `type_->serialize` inline under the writer mutex. The retained RMW source defaults to synchronous publication ([participant.cpp](/home/kkgiorgos/Chimaera/.chimaera-middleware/rmw_fastrtps-6.2.10/rmw_fastrtps_shared_cpp/src/participant.cpp:191)); the XML has no writer-mode override. A complete runtime environment/mode trace was not recorded here, so the default is source evidence, not proof that every send ran synchronously. Even asynchronous send mode would not remove this inline typed serialization.
- **Allocation needs a careful qualification.** The endpoint constructs/resizes the outgoing 8 MiB Image body in `setup_ball()` (line 370), then retains and reuses it in the publish lambda. It does **not** allocate a new 8 MiB outgoing Image vector for every release. ROS/DDS payload pools, receiving Image materialization, RTPS buffer assembly and host transport frame ownership can still copy or allocate large buffers. The exact Humble rclcpp executor implementation and generated Image CDR source were not found in the inspected retained source tree; installed `/opt/ros/jazzy` headers/templates are a different ROS release and are not treated as proof of the executed Humble allocation path. Allocation counts, sizes, reuse and time remain unmeasured.

**Transport and DDS locking: proven scope versus suspected delay**

The custom transport already has two lanes, each with its own send mutex, receiver worker, and guest `M5Endpoint`; host socket lanes also have their own writer/FIFO ([transport.cpp](/home/kkgiorgos/Chimaera/ros/chimaera_ros_ws/src/chimaera_dds_transport/src/transport.cpp:60)). Topic-specific ports select bulk/control through a reserved bit; Image topics default to bulk ([configure.cpp](/home/kkgiorgos/Chimaera/ros/chimaera_ros_ws/src/chimaera_dds_transport/src/configure.cpp:88)). The per-channel mutex surrounds delivery to `OnDataReceived` (transport line 120). The global channel-map mutex is released before this delivery. These source facts support transport-lane separation; they do not prove end-to-end latency isolation or an observed queue occupancy.

There **is** a participant-wide send lock above those lanes: [RTPSParticipantImpl::sendSync](/home/kkgiorgos/Chimaera/.chimaera-middleware/Fast-DDS-2.6.12/src/cpp/rtps/participant/RTPSParticipantImpl.h:269) locks `m_send_resources_mutex_` across calls to every sender resource. The custom sender calls `send_packet()` inline (transport lines 532–546). Consequently:

- On the host m5ops path, the critical section includes allocating an owned packet and copying the entire RTPS frame into its lane FIFO (transport lines 234–254). Blocking socket transmission is moved to the lane writer, outside this DDS callback. It would be incorrect to claim the DDS lock necessarily spans the host worker's wait for socket/router credit.
- On the guest path, it includes the lane lock and synchronous `M5Endpoint::send()` submission (transport lines 305–314; [m5_endpoint.cpp](/home/kkgiorgos/Chimaera/gem5-transport/src/m5_endpoint.cpp:127)). No per-call submission or participant-lock duration is retained. Even distinct source/executor threads sharing a participant can serialize at this stage.
- Reliable receive-side work can also need that **send** lock to send RTPS control traffic: [StatefulReader::send_sync_nts](/home/kkgiorgos/Chimaera/.chimaera-middleware/Fast-DDS-2.6.12/src/cpp/rtps/reader/StatefulReader.cpp:1446) calls participant `sendSync`. This is a source-established coupling opportunity, not evidence that a particular ACK or receive worker waited during either observed gap.

A participant-wide **receive** serialization claim is not established. [ReceiverResource::OnDataReceived](/home/kkgiorgos/Chimaera/.chimaera-middleware/Fast-DDS-2.6.12/src/cpp/rtps/network/ReceiverResource.cpp:100) locks that resource's mutex. [Participant receiver creation](/home/kkgiorgos/Chimaera/.chimaera-middleware/Fast-DDS-2.6.12/src/cpp/rtps/participant/RTPSParticipantImpl.cpp:1782) creates a `MessageReceiver` per new receiver resource. Its parser lock is instance-specific ([MessageReceiver.cpp](/home/kkgiorgos/Chimaera/.chimaera-middleware/Fast-DDS-2.6.12/src/cpp/rtps/messages/MessageReceiver.cpp:332)); `StatefulReader::processDataMsg` also uses its reader's mutex (line 514), as does `take`. Such locks can couple reception and take for the same reader, but these paths do not prove one participant-wide receive lock spanning independent topic channels. Shared CPU/memory resources and other DDS metadata paths remain possible contributors.

**No assumed 64 KiB fragmentation explanation**

The retained [DDS profile](/home/kkgiorgos/Chimaera/.chimaera-m5/timing-short-r3/short-bulk8m-direct_dds_m5ops-chimaera-shm-r1/dds.xml) configures SHM-only local transport with max message 9,433,088 bytes and a 64 MiB segment. The m5ops descriptor allows a 9 MiB complete CDDS frame minus its 52-byte header ([transport.hpp](/home/kkgiorgos/Chimaera/ros/chimaera_ros_ws/src/chimaera_dds_transport/include/chimaera_dds_transport/transport.hpp:18)); the participant hook normalizes local SHM to this transport limit (configure lines 148–160). An 8,388,676-byte serialized Image fits with RTPS overhead.

Fast DDS 2.6.12 explicitly supports large DATA submessages: [RTPSMessageGroup::add_data](/home/kkgiorgos/Chimaera/.chimaera-middleware/Fast-DDS-2.6.12/src/cpp/rtps/messages/RTPSMessageGroup.cpp:500) receives `is_big_submessage`, and [insert_submessage](/home/kkgiorgos/Chimaera/.chimaera-middleware/Fast-DDS-2.6.12/src/cpp/rtps/messages/RTPSMessageGroup.cpp:347) flushes a message containing a submessage larger than 64 KiB. [WriterHistory::set_fragments](/home/kkgiorgos/Chimaera/.chimaera-middleware/Fast-DDS-2.6.12/src/cpp/rtps/history/WriterHistory.cpp:284) fragments only after comparing serialized length with its calculated limit; the `uint16_t` fragment-size cap applies inside that branch. Thus the configuration/source can avoid fragmentation here. There is no retained RTPS packet trace or fragment counter to prove the actual DATA/DATA_FRAG count. Attributing the stalls to inevitable 64 KiB fragmentation is unsupported.

**Hypotheses and a bounded next architectural step**

The leading hypothesis is that the guest's sole executor spends long intervals inside the merged source's large publish path, then inside large typed takes, and drains old control work afterward. This matches the repeated bulk-adjacent source pauses, callback gaps, catchup bursts, and missing late releases. Source proves the execution dependencies; it does not prove their exact time shares. DDS serialization/copies/pool growth, the participant send lock, guest OS scheduling across two timing CPUs, DDS receive/history work, and m5 submission/service can all contribute. No profiling trace separates them, and application outstanding counts must not be relabelled as device/controller queue occupancy. The historical DMA queue failure is not proof of the same failure mechanism in the completed m5ops case.

The bounded next design change to consider is **benchmark-only separation of control from image traffic at both application execution and DDS participant boundaries**, before further transport tuning: independent control and image/bulk source loops, with image/bulk typed publication and take in a separate process/context/participant on each side. Include the normal camera images as well as supplemental bulk. Preserve routes, clocks, release schedules, payload identities, lossless semantics and event definitions; do not conceal missing releases by counting only eventual publications. A smaller callback-group/executor split addresses shared execution but retains the proven participant-send coupling, so it is not by itself a complete isolation design. Buffer reuse may reduce cost but must be measured rather than assumed; separate processes still share CPU and memory bandwidth.

A follow-up causal comparison should remain narrowly bounded and record publish entry/return, typed-take/deserialization boundaries, transport entry/exit, and participant-send lock wait/hold times with thread IDs and consistent clocks. It must report scheduled-release coverage and scheduled age alongside callback latency. This would distinguish the suspected application stall from transport/locking delay; repeated achieved-load windows would still be needed for a throughput/tail claim.
