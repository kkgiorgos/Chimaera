# Orchestrator preparation failure, 2026-10-23

Experiment: `7f683187d81043af9023cf734f116375`, using `m5ops` with Fast DDS.
The local supervisor records preparation starting at 02:19:56 and failing at
02:42:39 Europe/Athens. Its exit code was 1, with `oom: false`. No robot case
was launched by this supervisor.

## Cause and correction

The SDK and application images built, and Linux 5.15.180 compiled successfully.
The next step, building the external `chimaera_m5` module, failed:

```text
make[1]: *** No rule to make target 'chimaera_m5.mod', needed by '__build'. Stop.
```

`orchestrator/kernel/build.py` supplied `obj-m=chimaera_m5.o` as a command-line
make variable. GNU make gives that assignment precedence over Kbuild's own
assignments, including the rewriting of external module target paths. The same
selection mechanism also affected the DMA backend.

The driver Makefile now accepts `CHIMAERA_MODULES`, retaining both modules as its
default. The preparation recipe selects the requested module with that variable
and leaves `obj-m` writable by Kbuild. It still copies only the selected driver
source into the disposable build directory. Both changed files already
participate in the kernel asset cache identity, so the corrected recipe gets a
new cache key automatically.

Evidence remains under
`.chimaera-orchestrator/experiments/7f683187d81043af9023cf734f116375/`:
`kernel-build.log`, `worker.log`, and `preparation-report/failure.json`.
The experiment records and frozen inputs were left intact.

## Verification

The original command-line override reproduced an external module target failure
using real Kbuild from the installed Linux 6.5.0-41 headers. With the corrected
selection, the actual `chimaera_m5.c` compiled and linked to `chimaera_m5.ko`
against those headers, using only that source and the driver Makefile.

Regression tests exercise GNU make's variable precedence and Kbuild-style path
rewriting for each selected module and for the default pair. The mocked recipe
checks also verify the selection argument for both backends. The focused kernel
recipe/asset suite passed all 42 tests.

The full orchestrator/container regression suite passed all 289 tests:

```sh
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python3 -m pytest -q \
  orchestrator/tests containers/tests containers/ball-catching/tests
git diff --check
```

A separate DMA compilation against these newer host headers reached C compilation
but failed on its existing direct assignment to `vm_flags`, which is read-only in
that kernel API. This does not validate DMA on those headers; the orchestrator
targets Linux 5.15.180.

The full pinned Linux 5.15.180 build, driver ABI boot probe, and robot execution
were not rerun. Docker socket access is unavailable to this session.

## Recovery

The saved request freezes revision
`19b8712c62a877a69e7b18d4bd9ae195c444ac3d` and source fingerprint
`805efe7b3748f0784753ffdb3b8045b13bf99147093b49b87247ecfdd8d8961d`.
Applying this correction changes the source identity, so retrying preparation
on the existing experiment will fail its source identity check.

Stop the failed experiment, align the controller and worker checkouts with the
corrected sources, rebuild the controller and redeploy supervisors, then queue
a new experiment. Keep existing cached images and assets: matching build inputs
can still be reused. Validate the pinned kernel/module build and guest ABI probe
before treating the runtime issue as resolved.
