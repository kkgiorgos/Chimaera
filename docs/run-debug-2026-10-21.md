# Memory contention run debugging, 2026-10-21

Experiment: `45cb0456c6df40159630824cf632907f` (21 cases), prepared on
`ubuntu-george`, with four workers each on `ubuntu-george` and `pop-os`.

## Findings and corrections

1. All eight initial assignments remained `dispatching`, with controller events
   reporting `start: [Errno 2] No such file or directory: '/dev/kvm'`.
   Both hosts had `/dev/kvm` with group 109; neither supervisor container exposed
   that device. `containers/run.py` tried to stat the device inside the supervisor
   to choose the sibling worker's supplementary group, before recording a task.
   Deployment now reads the host group into `CHIMAERA_KVM_GID`. The supervisor
   supplies that group to the runner without needing the device itself. Both
   supervisors and the controller deployment code were updated. The original
   eight attempt IDs subsequently entered `running` and booted gem5.

2. The frozen experiment selected `fixed.transport_backend: dma` but omitted
   `fixed.dma_module`. Both machines used automatically generated disks, which do
   not contain the driver. Guest diagnostics reported
   `Guest bridge: open DMA device: No such file or directory`. Host startup
   cancellation and `m5_fail` were downstream symptoms. Preparation now rejects
   this combination before image building or guest construction. A custom disk
   may still omit the module when it already provides a loaded driver.

The guest serial logs also contained ATA lost-interrupt and disk I/O errors
during KVM boot. Their cause was not established in this investigation. A corrected
DMA configuration still needs a real single-case boot validation.
